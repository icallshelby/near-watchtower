# NEAR Watchtower

**A network-health agent for NEAR Protocol — with an open lab around it.**
The agent polls live public data, scores the network's health from evidence,
watches its own history for anomalies, and publishes a machine-readable feed
that other agents act on. A second, demo agent in this repo consumes the feed
and makes (simulated) allocation decisions from it. The dashboard is an
interactive lab: visitors can re-weight the scoring model and watch the score
recompute from the same evidence — the methodology is inspectable, never a
black box.

- Live status page: `index.html` (rendered by `build_dashboard.py`, fully
  self-contained, works offline once generated)
- The feed: `data/status.json` — score, label, components, alerts, evidence
- The audit trail: `data/snapshot_raw.json` — every raw API response used
- The time series: `data/history.jsonl` — one line per agent run, committed
- The consumer's decisions: `data/agent_log.jsonl`
- The plain-language version: `BRIEF.md`
- Demo video: a screen recording of the lab in use ships with the project's
  demo post (and can be regenerated by recording `index.html` locally)

Team: **zarroww** · NEAR Hackathon — Agent Economy track

## The problem

The agent economy has a trust problem. Thousands of autonomous agents are
starting to hold funds, route trades and choose staking providers on NEAR —
but every one of them answers the most basic question ("is the network
healthy right now?") in its own private way, from its own private data, or
worse, from a dashboard screenshot a human pasted into a prompt. There is no
shared, public, recomputable answer.

Centralized status pages don't fix this: they are opinions rendered as HTML,
with no audit trail an agent can verify. An agent that pauses a treasury on
the strength of a green dot it cannot recompute is not being careful — it is
being obedient.

**Watchtower is the missing public signal:** one small agent whose only job
is to watch the network, score it from evidence, publish the evidence with
the score, and flag when reality drifts from its own history. Any other
agent can consume the signal *and* audit it, because every input ships with
the output. Trust is replaced by recomputation.

## Why NEAR makes this possible (and necessary)

- **Speed makes "live" meaningful.** NEAR produces a block roughly every
  0.6 seconds — about 151,000 blocks a day. A health signal sampled hourly
  would be archaeology; Watchtower's evidence is minutes old at worst.
- **The validator set is public and complete.** NEAR's RPC returns the full
  live validator set with stakes, so decentralization can be *summed*, not
  estimated — the Nakamoto coefficient in this feed is computed pool by
  pool, not copied from a third-party chart.
- **The agent economy is the consumer.** NEAR is explicitly building for
  intents and autonomous agents. Agents that transact around the clock need
  a machine-readable risk signal in exactly the way human traders needed
  price feeds a decade ago. Watchtower is that feed for network health.

## A worked example — the current snapshot, narrated

From `data/status.json` (regenerated on every run):

- **Score 83.2 / 100 — STRONG.** Cadence 95.2 (blocks landing every 0.571s
  against a 0.6s target), throughput 100 (151,208 blocks/day), liquidity
  96.9 (24h turnover is 11.63% of the $4.68B market cap).
- **The honest weak spot: decentralization 60.0.** The Nakamoto coefficient
  is 9 — the nine largest pools together hold just over a third of all
  stake; the top 10 hold 36.25%, the largest single pool 5.71%. The feed
  does not hide this behind the headline score; it is the first thing the
  demo consumer agent reports ("weakest component: decentralization").
- **Staking 73.8:** 44.31% of all NEAR is staked across 339 validators,
  with 371 nodes online and 5.478 billion lifetime transactions served.

The demo consumer agent reads exactly this and decides: STRONG → 70%
growth / 30% reserve, no operator alert, weakest component noted. Change
one number — say the coefficient falls to 4 — and the same code path caps
growth and raises an alert. That is the whole thesis in miniature: shared
evidence in, accountable decisions out.

## How to use it

### If you are a person (no code)

1. Open the live status page (this repository's Pages/Vercel deployment, or
   `index.html` locally after the run below). The big number is the network's
   health score right now, out of 100, with a label: STRONG, STEADY, FRAGILE
   or CRITICAL.
2. The five component bars tell you *why*: block cadence, decentralization,
   staking, throughput, liquidity. The alerts box tells you if anything moved
   abnormally versus the agent's own history.
3. **Try the lab:** drag the weight sliders (or use a preset like
   "Decentralization maximalist" or "Markets only") and watch the gauge
   recompute. The evidence never changes — only the judgement applied to it.
   That is the point: a health score is a policy, and here the policy is
   yours to inspect and challenge.
4. `BRIEF.md` is the same snapshot in plain sentences.

### If you are an agent or an app

Fetch `data/status.json` and read the score, the label, the components, the
alerts and the evidence:

```json
{
  "health_score": 83.2,
  "health_label": "STRONG",
  "components": { "cadence": 98.0, "decentralization": 60.0, "staking": 73.8,
                  "throughput": 100.0, "liquidity": 96.1 },
  "alerts": [ { "component": "staking", "kind": "z_score",
                "detail": "staking is -2.3 sigma vs its own history ..." } ],
  "evidence":   { "nakamoto_coefficient": 9, "staked_pct_of_supply": 44.31 },
  "generated_at": "2026-11-09T12:55:15Z"
}
```

Concrete uses:

- **Trading / treasury agents** — gate position size or pause execution when
  `health_label` drops below `STEADY` (a working example is in this repo:
  `agent_consumer.py`, policy below).
- **Staking dashboards** — page an operator when `alerts` reports the
  Nakamoto coefficient drifting.
- **Wallets** — show a network status dot (green/amber/red from the label)
  computed from public evidence instead of a hard-coded "all good".
- **Researchers** — diff successive snapshots; every input is preserved in
  `snapshot_raw.json`, so any score can be recomputed by hand.

### Run the whole system yourself

```bash
python3 watchtower.py        # fetch live data -> feed, brief, history, alerts
python3 agent_consumer.py    # a second agent acts on the feed (simulation)
python3 build_dashboard.py   # render the interactive lab (index.html)
```

Python 3 standard library only. No API keys, no accounts, no dependencies,
no wallet, nothing is ever signed or spent.

## How the score works

A weighted sum of five components, each 0–100, each computed from live data.
The weights are policy — stated here so anyone can disagree productively:

| Component | Weight | What it measures | Full marks when |
| --- | --- | --- | --- |
| Cadence | 20% | Average block time vs the ~0.6s the network runs at | blocks land at the target cadence |
| Decentralization | 25% | Nakamoto coefficient — smallest number of validator pools holding >1/3 of stake, summed directly from the live RPC validator set | coefficient of 15 |
| Staking | 20% | Share of total supply staked | 60% of supply staked |
| Throughput | 15% | Estimated blocks per day | 144,000 blocks/day |
| Liquidity | 20% | 24h trading volume as a share of market cap | 12% daily turnover |

Labels: **STRONG** ≥ 75 · **STEADY** ≥ 55 · **FRAGILE** ≥ 40 · **CRITICAL** < 40.
The score deliberately excludes price prediction: the price appears only as
evidence (drawdown from ATH), never as a score input beyond liquidity's
turnover ratio.

## Anomaly detection

Every run compares the fresh snapshot against the agent's own committed
history (`data/history.jsonl`):

- any component under 40 flags immediately (`low_component`);
- a health-label change flags (`label_change`);
- once at least 5 snapshots exist, a component also flags when it sits at
  |z| ≥ 2 against its own history mean (`z_score`).

Alerts are part of the feed, so downstream agents react to the same signals
a human sees on the dashboard.

## The consumer agent's policy

`agent_consumer.py` is a demo treasury agent — **simulation only, no real
funds, no keys, no transactions**. It reads the feed and sets a risk budget:

| Label | Growth / reserve |
| --- | --- |
| STRONG | 70 / 30 |
| STEADY | 50 / 50 |
| FRAGILE | 20 / 80 + operator alert |
| CRITICAL | 0 / 100 + operator alert |

Any active watchtower alert caps the growth share at 20% regardless of the
label. Every decision, with its reasons, is logged to `data/agent_log.jsonl`
and shown on the dashboard.

## Data sources

| Source | Used for |
| --- | --- |
| NearBlocks API (`api.nearblocks.io/v1/stats`) | supply, price, market cap, 24h volume, ATH, lifetime transactions, nodes online, block time |
| NEAR mainnet RPC (`status`, `validators`) | chain status, latest block, and the full live validator set — stake shares, the staking total and the Nakamoto coefficient are summed locally from it |
| CoinGecko public API | market data cross-check (price, market cap, ATH) |

Supply figures come from NearBlocks (yocto-denominated, divided by 10²⁴)
because CoinGecko's circulating-supply field for NEAR currently mirrors total
supply; every derived value can be checked against `data/snapshot_raw.json`.

## Limitations, honestly

- Snapshots, not a stream: re-run the agent to refresh. The commit history
  of `data/` is the time series; z-score alerts need a handful of runs
  before they mean anything, and the code says so.
- The component targets (0.6s cadence, NC 15, 60% staked, …) are stated
  editorial choices, not protocol constants — the dashboard lab exists
  precisely so visitors can test other choices.
- The consumer agent is a policy demonstration with a mock allocation. It
  moves no funds; wiring it to a real treasury is out of scope by design.
- If a source is unreachable, the run fails loudly rather than scoring
  stale data as if it were live.

## For judges — the 60-second tour

1. `python3 watchtower.py` — watch it fetch live data and print the score.
2. `python3 agent_consumer.py` — watch a second agent act on the feed and
   explain its decision, citing the weakest component by name.
3. `python3 build_dashboard.py`, open `index.html`, drag the
   **decentralization** slider to zero and back: the gauge recomputes live.
   That interaction is the argument — the model is policy, the evidence is
   fact, and the two are never confused.
4. Open `data/history.jsonl` and `data/agent_log.jsonl`: the system's
   memory and the consumer's accountability trail, both committed in git.

## Sustainability & roadmap

Running Watchtower costs nothing and needs no babysitting: three stdlib
scripts, public keyless APIs, static hosting. Run it on a cron and the
history file becomes an asset — a public, timestamped, recomputable record
of NEAR's structural health that gets more valuable the longer it runs.
Plausible next steps, in order: alert webhooks for operators; more
components (bridge flows, intents volume, shard count over time); signed
snapshots so consumers can verify origin as well as content; the same
agent pattern ported to a second chain for comparison. None of that changes
the contract: evidence first, score second, decisions third.

## FAQ

- **Is this financial advice?** No. The score summarizes network structure;
  it never predicts price, and the consumer agent is a simulation with no
  funds, keys or transactions — by design.
- **Why not a smart contract?** The inputs live off-chain (public APIs);
  an oracle would add a trusted party to a system whose entire point is
  that nobody has to be trusted — anyone can re-run the agent and compare.
- **Why should anyone trust the score?** They shouldn't. They should
  re-run it: `snapshot_raw.json` plus the published weights reproduce
  every figure, and the dashboard lab exists so even the *policy* can be
  challenged without reading code.
